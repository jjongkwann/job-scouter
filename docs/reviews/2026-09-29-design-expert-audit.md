# Job Scouter 독립 디자인 감사

점검일: 2026-09-29. 대상: 운영 `http://192.168.0.5:8090`, 배포 기준 `a61c5bc`.

정보 밀도가 높은 업무용 웹앱의 제품 디자인·UX 관점에서 점검했습니다. 구현자의 의도나 테스트 통과를 완성도의 증거로 사용하지 않았습니다. Chrome의 실제 배포 화면과 DOM 치수를 확인하고 해당 소스를 대조했습니다. 제품 코드 변경과 배포는 수행하지 않았습니다.

기준은 `docs/design.md`, `docs/plans/2026-09-29-ui-audit-and-redesign.md`, `README.md`, `../sharer/docs/design.md`입니다. **정보의 정확성 → 사용자 통제 → 작업 연속성 → 탐색·읽기 효율 → 시각 정돈** 순서로 우선순위를 정했습니다.

## 판단

다섯 업무 영역, 상태를 구분하는 문구, 문서 본문과 모바일 탐색은 일관된 기반을 갖췄습니다. 남은 핵심 문제는 작업 진입점과 판단 근거의 배치입니다. 이력서 갱신 제안은 긴 문서 뒤에 숨고, 제안의 높은 점수 앞에서는 중요한 자격 차이를 볼 수 없으며, 초안 폴더를 바꾸면 읽던 문서와 위치를 잃습니다.

새 메뉴 체계나 시각 스타일을 다시 만들 필요는 없습니다. 현재 구조에서 중요한 정보의 순서와 읽던 위치를 먼저 바로잡는 것이 적절합니다.

## 확인 범위와 증거 방식

- 너비 360·390px 모바일, 1093px 좁은 데스크톱, 1440px 데스크톱에서 대표 화면을 직접 관찰했습니다. 각 경로를 모든 너비에서 반복한 검사는 아닙니다.
- 증거는 라이브 DOM의 텍스트·속성·치수와 `source file:line`으로 기록했습니다. 독립 감사에서 별도 스크린샷 파일을 저장하지 않았으며, 메인 에이전트의 교차검증 이미지 한 장을 아래에 참조합니다. 수치는 문서 내용과 뷰포트 높이에 따라 달라질 수 있습니다.
- 승인·후보 선택 처리·제외·초안 생성·이력서 저장·복원·외부 응답은 실행하지 않았습니다. 탐색, 문서 탭, 접기/펼치기, 폴더 전환, 파일 검색만 조작했습니다.
- `viewport.reset()`을 실행하고 기본 1093×963px 복원을 확인했습니다.
- **확정 결함**은 실제 화면에서 재현한 기능·표현 문제, **디자인 개선 권고**는 관찰한 화면에 대한 개선 판단, **미검증 가설**은 소스에서 가능성을 확인했으나 운영 상태를 재현하지 않은 항목입니다.

## 유지할 점

1. **주 메뉴·영역 메뉴·문서 탭의 역할이 구분됩니다.** 데스크톱 사이드바와 모바일 하단 메뉴가 같은 다섯 라벨을 유지하고, 영역 메뉴의 밑줄과 문서 선택 상태가 보입니다. 주 메뉴에는 `aria-current`가 있습니다. `web/components/nav.tsx:21`, `web/components/nav.tsx:45`.
2. **상태의 과장을 줄였습니다.** 제안에는 원티드 응답·내부 검토·평판을 각각 표시하고 기한과 수집 시점을 노출합니다. 초안과 제출용 파일은 실제 지원 완료와 구분합니다. `web/app/offers/page.tsx:64`, `web/components/application-files.tsx:47`.
3. **문서 탭의 조작과 선택 표시가 안정적입니다.** 360px에서 탭 높이 44px, 줄바꿈 후 선택 라벨이 읽혔습니다. 방향키로 초점만 이동하고 Enter로 선택되는 동작과 초점 테두리를 확인했습니다. `web/app/applications/doc-tabs.tsx:33`.
4. **긴 문서의 기본 읽기 규칙이 적용돼 있습니다.** 사실베이스의 실제 문단은 16px, 1440px에서 약 786px 읽기 폭이었습니다. 360px에서는 페이지 폭 360px을 유지하고, 넓은 표는 294px 영역 안에서 자체 스크롤 폭 500~600px을 갖습니다. `web/app/globals.css:134`.
5. **일부 빈 상태는 다음 상황을 설명합니다.** 파일 검색은 `0 / 120세트`와 ‘검색 결과가 없습니다’를 보여줍니다. 갱신 제안 0건은 데이터 없음의 의미를 설명하고 반영 버튼을 비활성화합니다. `web/app/applications/files/page.tsx:32`, `web/app/resume/proposals/page.tsx:73`.

## 핵심 개선점

### 1. P1 · 확정 결함 — 이력서의 갱신 제안 진입점이 긴 본문 끝으로 밀립니다

**위치·재현:** `/resume`, 1280px 미만. 페이지 상단에서 갱신 제안이나 진행 중 대화를 찾습니다.

**관찰 근거:** 360px에서 ‘진행 중 대화’ 제목은 y=66,948px, ‘갱신 제안’은 y=67,033px, ‘갱신 제안 보기’ 링크는 y=67,144px에 위치했습니다. 1093px에서도 링크는 y=36,413px입니다. 현재 대화와 대기 제안은 0건이지만 진입점이 본문 끝에 놓이는 현상은 실제 확인했습니다. `web/app/resume/page.tsx:32`의 한 열 레이아웃에서 전체 Markdown 다음에 `:43`의 작업 카드가 나옵니다. 이력서 영역의 보조 메뉴도 없습니다(`web/components/nav.tsx:35`).

**영향:** 사용자는 갱신 제안 기능을 발견하기 어렵고, 대화가 있을 때도 상단의 ‘대화로 고치기’만 보고 기존 작업을 놓칠 수 있습니다. 후자는 현재 대화 0건이므로 데이터가 있는 상태의 직접 검증은 아닙니다.

**최소 수정안:** 좁은 화면에서는 진행 중 대화와 갱신 제안 진입점을 본문 앞에 배치합니다. 상단 행동 영역에 ‘갱신 제안 0건’ 링크를 두고, 대화가 있을 때는 이어가기 링크를 같은 영역에 둬도 됩니다. 문서 본문을 축약하거나 새 전역 메뉴를 추가할 필요는 없습니다.

**완료 기준:** 360·390·1093px에서 본문을 끝까지 내리지 않고 갱신 제안과 진행 중 대화에 도달합니다. 실제 대화/제안이 있는 격리 데이터로 기존 작업이 상단에 나타나는지 확인합니다.

### 2. P1 · 확정 결함 — 높은 적합도·파일 행동보다 중요한 조건이 뒤에 숨습니다

**위치·재현:** `/offers` 기본 카드, `/applications/files` 및 공고 상세의 제출용 파일 카드에서 보고서/확인 사항을 펼치기 전후를 비교합니다.

**관찰 근거:** 받은 제안의 한 기본 카드에는 ‘등록된 공고 적합도 88점’과 ‘후보 등록’이 보이지만, 보고서를 펼쳐야 ‘조건부 지원 검토’와 필수 인프라 경험의 차이가 나타납니다. 기본 본문은 ‘기존 후보 메모: 미등록’이어서 중요한 차이를 대신 설명하지 못합니다. `web/app/offers/page.tsx:74-80`은 보고서 전체를 닫힌 `details`로 렌더링합니다. 파일 카드에서도 실제 경력의 범위·미보유 역량을 담은 ‘경험 범위·지원 전 확인’이 보기/다운로드 6개 행동 뒤에 접혀 있습니다(`web/components/application-files.tsx:48-74`).

**영향:** 점수와 생성된 파일이 먼저 준비 완료의 인상을 만들고, 판단을 제한하는 조건은 추가 조작을 해야 알 수 있습니다. 개편 원칙의 ‘자격 미충족·중요 감점 이유를 접힘에 숨기지 않는다’와 맞지 않습니다.

**최소 수정안:** 제안의 판단 요약과 확인된 필수요건 차이를 점수 가까이에 상시 표시하고, 긴 보고서 본문만 접습니다. 파일 카드의 확인 사항 중 지원 전 필요한 제한은 파일 행동 앞에 짧게 표시합니다. 단순 ‘주의 있음’ 배지만으로 내용을 대신하거나 파일 열기를 강제 차단하지 않습니다.

**완료 기준:** 접힌 기본 카드만 읽어도 사용자가 점수의 조건과 주요 자격 차이를 설명할 수 있습니다. 360px에서도 파일을 받기 전에 해당 제한을 볼 수 있고 원문 전체는 펼쳐 읽을 수 있습니다.

### 3. P2 · 확정 결함 — 초안 버전을 구별하기 어렵고, 전환하면 읽던 탭·위치를 잃습니다

**위치·재현:** `/applications/job/384841`의 복수 폴더, `/applications/job/383001`에서 ‘맞춤 이력서’ 탭을 읽다가 다른 기존 폴더로 전환합니다.

**관찰 근거:** 첫 사례의 서로 다른 두 폴더가 모두 **‘원본 · 2026-09-14’**로 표시됩니다. `aria-label`에는 서로 다른 폴더 식별자가 있지만 눈으로 보는 라벨에는 차이가 없습니다. `web/app/applications/job/[cid]/page.tsx:191`은 `_draft` 접미사만으로 원본/재생성본을 정합니다. 두 번째 사례는 폴더 전환 후 선택 탭이 ‘맞춤 이력서’에서 ‘공고’로 돌아가고 `scrollY=0`이 됐습니다. 360px에서 문서 시작은 y=1,634px였습니다. 폴더 전환은 `:182`의 `router.replace`, 로딩 중 전체 화면 교체는 `:65-70`, 탭 상태는 `web/app/applications/doc-tabs.tsx:21-23`에 있습니다. 메인 에이전트도 별도 탭에서 동일 라벨을 재현하고 `data/design-expert-audit-20260929/folder-labels-main.png`에 저장했습니다.

**영향:** 같은 날짜의 문서 중 무엇을 읽는지 판단하기 어렵고, 버전 비교 때마다 문서 탭을 다시 선택하고 내려가야 합니다. 파일 버전의 의미를 사용자가 추측하게 합니다.

**최소 수정안:** 표시 라벨에 식별 가능한 폴더명 또는 기록으로 확인되는 생성 구분을 포함합니다. 확인되지 않은 모든 폴더를 ‘원본’으로 단정하지 않습니다. 폴더 전환 시 현재 문서 종류를 유지하고 문서/폴더 선택 영역에서 읽기를 계속하도록 합니다. 해당 문서가 없을 때만 그 이유와 대체 선택을 알립니다.

**완료 기준:** 같은 수정일의 두 폴더를 표시 이름만으로 구별할 수 있습니다. ‘맞춤 이력서’를 읽던 상태에서 양쪽 폴더를 왕복해도 해당 탭과 읽기 진입 위치를 유지합니다.

### 4. P2 · 디자인 개선 권고 — 좁은 데스크톱의 초안 목록·상세를 너무 일찍 한 열로 바꿉니다

**위치·재현:** 1093px에서 `/applications`와 공고 상세를 봅니다.

**관찰 근거:** 초안 목록 첫 행은 폭 약 849px, 높이 약 234px인데 회사·폴더, 직무·ID, 추천도, 마감, 초안 수, 수정일이 모두 세로로 나뉩니다. 900px 높이 첫 화면에서 두 행만 온전히 보입니다. 상세에서도 넓은 적합도 막대 아래로 마감·근무지·평판이 한 항목씩 쌓입니다. 목록 `web/app/applications/page.tsx:10`, `:78-116`과 상세 `web/app/applications/job/[cid]/page.tsx:114`가 1280px 이하를 일괄 한 열로 처리합니다.

### 5. P2 · 디자인 개선 권고 — 수백 건의 목록에서 특정 공고를 다시 찾는 도구가 부족합니다

**최소 수정안:** 기존 파일 검색과 같은 단순한 회사·직무·ID 텍스트 필터를 후보/초안 목록 상단에 둡니다. 현재 표시 건수와 전체 건수를 구분합니다. 파일 검색도 통계 다음으로 올립니다. 서버 검색 체계나 새로운 검색 페이지는 필요하지 않습니다.

**완료 기준:** ID나 회사명의 일부로 해당 공고·폴더를 바로 찾고 결과 0건을 식별할 수 있습니다. 검색을 지워 원래 목록으로 돌아갈 수 있으며 후보 상세 왕복 시 검색·정렬 상태가 유지됩니다.

**완료 기준:** 원문 링크가 있는 미연결 문서에는 링크 추가 안내가 나오지 않습니다. 후보 미존재·원문 링크 없음·연결 미확인을 각각 실제 근거 범위 안에서 설명합니다.

### 8. P2 · 미검증 가설 — 일부 쓰기 요청 실패가 지속되는 복구 안내를 남기지 않을 수 있습니다

**위치·재현 조건:** 승인 요청·후보 제외 요청·이력서 복원 요청 자체가 네트워크/API 오류로 실패하는 상태. 운영 데이터에서는 재현하지 않았습니다.

**최소 수정안:** 별도 알림 시스템을 만들지 않고 해당 작업 영역에 기존 오류 상태와 재시도 방법을 남깁니다. 서버가 요청을 수락했는지 불분명한 경우 결과 확인 경로를 먼저 제시하고 중복 작업을 유도하지 않습니다.

**완료 기준:** 격리 데이터/API에서 요청 접수 실패와 실행 후 실패를 각각 재현합니다. 토스트가 사라진 뒤에도 대상·실패 이유·남은 선택/입력·복구 경로를 확인할 수 있어야 합니다.

## Sharer 원칙의 적용 판단

내용 우선, 44px 조작, 안정된 탐색, 실패를 화면의 일부로 취급하는 원칙은 Job Scouter에도 적합합니다. 현재 색·경계·사이드바를 바꿀 이유는 확인하지 못했습니다. 점수별 전체 카드 채색이나 새 장식은 필요하지 않습니다.

‘정보를 필요한 순간에 보여준다’는 원칙을 적용할 때, 채용 판단을 바꾸는 조건은 기본 카드에 남아야 합니다. 항목 2는 이 경계가 약한 사례입니다. ‘자료가 먼저 보인다’ 역시 문서 본문 뒤에 작업 진입점을 두라는 뜻으로 적용하면 업무 연속성이 떨어집니다. 항목 1처럼 먼저 돌아갈 작업을 찾을 수 있게 한 뒤 본문을 읽도록 해야 합니다.
