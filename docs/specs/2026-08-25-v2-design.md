## 작업 지도 (6번)

| 하던 일 | 분류 | v2에서 |
|---|---|---|
| 공고 수집·판정·등재 후보 | 자동 | DailyScan |
| 등재 승인 | 사람(웹) | 대시보드 버튼 → `Publish` 워크플로 |
| 원티드 매칭률·잡플래닛 리뷰 | 대화형(로그인 크롬) | 대시보드가 「평판 미조사 회사」 목록 제시 → 작업 머신 `/job-scout` 브라우저 단계 → 기업평판.md push |
| refresh_due·build·스냅샷·보고서 | 자동 | Publish 끝에 실행. 후보목록.html은 웹앱이 서빙 |
| 회사별 지원서류 5종 | 자동 초안 + 대화형 다듬기 | Publish에서 승인 공고별 `draft_application` → applications/{회사}/ 커밋 |
| JK.md·사실베이스 갱신 | 자동 제안 + 사람 승인 | ResumeSync |
| 원티드 프로필·output docx/pptx | 대화형 | 변경 없음(사이트에서 열람만) |
| 지원이력·지원스케줄·Gmail 결과 | 대화형 | 사이트 열람. Gmail은 headless MCP 불가 |
| references(백엔드 노트 등) | 열람 | 사이트 `/docs` |

## 구조

```
서버 (OrbStack compose)              데이터: GitHub private <private-data-repo>
 ├─ temporal   :7233/:8233            ├─ 서버 clone  /work/repo  (컨테이너 마운트)
 ├─ io         워커 (git·fetch·ES·build)└─ 작업 머신 clone  (대화형 세션)
 ├─ llm        워커 (claude -p: judge·draft·resume·report)
 ├─ web        FastAPI :8090  ← 사람은 여기만 본다
 └─ (host) ES :9200 — jobscout_* + pkb_documents(ResumeSync만 읽음)

Schedules: DailyScan 매일 09:07 KST · ResumeSync 매주 월 08:00 KST (겹치면 skip)
```

### 워크플로 3개

**DailyScan** — 무인. sync_repo → fetch → load_targets → judge×N(예산·캐시) → `jobfeed/proposals.json` 갱신(신규 비제외 판정 누적, 이미 등재·제외된 id 제거) → commit+push. 판정 0건이면 LLM 0.

**Publish(ids)** — 웹앱 버튼이 시작. sync_repo → commit_rows(승인 행) → refresh_due → build → draft_application×승인건(llm) → commit+push → report. 사람이 안 고른 후보는 proposals에 남는다(다음 스캔에서 재판정 안 함 — 캐시). 「거부」 버튼은 `skipped`에 사유와 함께 기록(다음 fetch에서 안 뜸).

**ResumeSync** — 주 1회. pkb_documents에서 `status=curated`·경력/프로젝트 카테고리 문서를 읽어 해시 → `data/resume_state.json`의 지난 해시와 같으면 종료(LLM 0). 다르면 llm `propose_resume_update(pkb 발췌, 사실베이스, JK.md)` → 변경 제안(추가/수정/삭제 항목 + 근거 문서) `jobfeed/resume_proposals.json` → push → 웹앱 `/resume/proposals`에서 항목별 승인 → `ApplyResume` 워크플로: 사실베이스·JK.md 패치 커밋+push + `index_es.py`(사실베이스 재색인). 사실베이스 해시가 바뀌므로 judge 캐시는 자연 무효화(설계 그대로).

### 데이터 경계 개정
- judge·draft는 여전히 PKB 인덱스를 읽지 않는다. **PKB 읽기는 ResumeSync 하나뿐**이고, 결과는 사람 승인을 거쳐 사실베이스·JK.md에만 들어간다(PKB 원문이 judge 프롬프트에 직접 실리는 경로 없음).
- 웹앱은 LAN 전용(:8090), 무인증(Temporal UI와 동일 수준). 포트포워딩 금지.
- Claude Code 구독 인증은 llm 컨테이너 env(`CLAUDE_CODE_OAUTH_TOKEN`)에만.

### 웹앱 (FastAPI + markdown 렌더, DB 없음 — 데이터 repo 파일이 상태)
| 경로 | 내용 | 쓰기 |
|---|---|---|
| `/` | proposals(점수·사유·인용·conf) + 승인/거부 체크 → Publish 시작 · 평판 미조사 회사 · 최근 사이클 상태(Temporal query) | Temporal client |
| `/candidates` | build.py 산출 후보목록.html 그대로 | — |
| `/reports` | jobfeed/reports/*.md 목록·렌더 | — |
| `/resume` | JK.md·사실베이스·drafts/ 렌더, `/resume/proposals` 승인 | ApplyResume 시작 |
| `/applications/{회사}` | 5종 md 렌더 | — |
| `/docs` | references/ 렌더 | — |

### 지원서류 초안 (`draft_application`)
입력: 공고 전문(자격요건·주요업무·우대 — 300자 캡 아님, judge와 달리 전문), 사실베이스, JK.md, `applications/README.md` 규칙, 기존 1개사 예시(형식 앵커). 출력: 5개 md(0_JD·1_맞춤_이력서·2_자기소개서·3_면접지식맵·4_포트폴리오_구성) + README 체크리스트. 사실베이스에 없는 주장 금지(judge와 같은 원칙). 회사당 ~$0.3 상당.

### 기각한 대안
- 승인을 Temporal UI signal로: 동작하지만 proposals 내용을 보며 고르는 UX가 없어 웹앱 채택.
- 지원서류 전체 자동: 후보 전건이면 토큰 낭비 — 승인 건만.
- ResumeSync가 JK.md를 직접 수정: 사실베이스 사람검증 원칙(2026-08-11 사고) 위반 — 제안·승인 구조.
