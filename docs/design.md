# Job Scouter 디자인 원칙

결정일: 2026-09-29. 이번 UI 개편과 이후 기능의 화면 설계 기준입니다. 원칙과 목표를 확정한 문서이며, 구현 완료를 뜻하지 않습니다. 구현 순서와 관찰된 결함은 [화면 점검·수정 계획](plans/2026-09-29-ui-audit-and-redesign.md)에 기록합니다.

## 제품의 목적

**근거를 확인하고, 직접 판단하며, 지원 준비를 이어가는 개인 채용 작업공간을 만듭니다.**

공고 수집·평가·초안 작성은 반복 작업을 줄입니다. 사용자는 지원 자격과 경력의 차이, 근무 조건, 평판의 근거를 확인하고 후보를 선택합니다. 선택한 공고의 조사·서류·수정 이력이 연결되어, 다시 열었을 때 남은 일을 알 수 있어야 합니다.

현재 프로젝트의 기반은 사람이 결정하는 지점을 보존하는 자동화, 사실베이스에 따른 평가, 공고 ID에 따른 자료 연결, 기록 보존입니다. 화면도 이 구조를 그대로 설명해야 합니다. 현재 경계는 [README](../README.md)의 승인·초안·이력서 저장 흐름을 기준으로 합니다. 초기 설계 문서의 과거 실행 환경을 현재 동작으로 간주하지 않습니다.

판단이 충돌할 때의 우선순위는 **정보의 정확성 → 사용자의 통제 → 작업의 연속성 → 탐색·읽기 효율 → 시각적 정돈**입니다.

## 1. 판단에 필요한 근거를 먼저 보여줍니다

목록에서 회사·포지션, 마감, 확인된 필수 자격의 충족 여부와 미확인 항목, 짧은 판정 사유를 볼 수 있어야 합니다. 자격 미충족, 중요한 감점 이유, 응답 기한은 접힌 영역에 숨기지 않습니다. 긴 설명·전체 인용·세부 점수는 펼쳐 확인합니다.

적합도는 경력과 직무의 부합 정도, 추천도는 검토 순서를 정하는 보조값입니다. 점수를 지원 자격이나 합격 확률처럼 표현하지 않습니다. 모델의 확신도도 실제 합격 가능성으로 표시하지 않습니다. 필요한 근거가 없으면 ‘미확인’으로 남깁니다.

원문·평가·기업 조사에는 해당 정보의 출처와 확인 시점을 표시합니다. 최신 여부를 알 수 없으면 그 한계를 설명합니다. 목록에 여러 공고를 나란히 놓더라도 각 공고의 평가와 필수 요건은 독립적으로 유지합니다.

## 2. 자동화의 범위와 결과를 예측할 수 있게 합니다

설정된 자동 수집·평가를 유지합니다. 후보 승인은 기존처럼 등재 처리와 후속 초안 생성을 시작하며, 버튼 주변에서 그 결과를 알립니다. 화면 이동과 자료 열람은 생성·지원·외부 응답을 시작하지 않습니다.

`후보 등록`, `후보에서 제외`, `초안 만들기`, `이력서에 저장`, `원티드에서 답변`을 구별합니다. 실제 영향을 설명하지 않는 ‘제출’ 같은 문구를 사용하지 않습니다. 일괄 작업은 대상과 건수를 표시하고 기존의 필요한 확인·잠금 동작을 유지합니다.

요청 접수·실행 중·완료·일부 실패를 실제 처리 결과에 맞게 보여줍니다. 후보 등록이 끝나고 초안 생성만 실패했다면 두 결과를 따로 표시합니다. 실패 안내와 가능한 복구 행동은 화면에 남기며, 입력과 선택을 불필요하게 버리지 않습니다. 실행 단계와 진행률을 알 수 없으면 추정값을 만들지 않습니다.

## 3. 공고와 제안의 맥락을 끝까지 유지합니다

공고의 원문, 평가, 조사 보고서, 후보 상태, 초안, 제출용 파일을 확인된 ID·연결 정보로 이어 줍니다. 같은 회사라는 이유만으로 다른 직무를 합치지 않습니다. 공고에 아직 연결되지 않은 받은 제안도 자체 ID와 원문을 가진 항목으로 유지합니다.

후보에서 상세를 열고 돌아오면 필터·정렬·목록 위치를 유지합니다. 페이지마다 같은 회사·직무를 다시 검색하게 하지 않습니다. 다른 자료로 이동해도 현재 대상과 상위 목록으로 돌아가는 경로가 보여야 합니다.

목록은 우선순위를 정하는 곳, 상세는 근거를 읽고 준비하는 곳으로 역할을 나눕니다. 연결되지 않은 자료는 그대로 표시하며 임의의 연관 관계를 만들지 않습니다.

## 4. 상태와 문서의 의미를 섞지 않습니다

| 구분 | 화면에서 답해야 할 질문 | 표시 원칙 |
| --- | --- | --- |
| 공고 상태 | 지금 모집 중인가? | 모집·마감과 확인 시점을 구별 |
| 검토 상태 | 내가 후보로 선택했는가? | 승인 대기·후보 등록·제외를 실제 기록으로 표시 |
| 제안 응답 | 회사의 제안에 답했는가? | 원티드의 응답 상태를 내부 후보 상태와 구별 |
| 서류 준비 | 무엇이 생성되어 있는가? | 없음·생성 중·일부 생성·초안·제출용 파일을 구별 |
| 사용자 검토 | 내용 확인이 끝났는가? | 명시적인 기록이 있을 때만 ‘검토 완료’로 표시 |
| 실제 지원 | 외부에 지원서를 제출했는가? | 파일·폴더 존재로 추정하지 않음. 추적하지 않으면 상태를 만들어 표시하지 않음 |

공고 원문·사실베이스는 근거이고, AI 평가·조사 결과는 판단 자료입니다. 초안은 수정할 문서이고 PDF·PPTX는 출력 형식입니다. 파일 생성만으로 사용자 검토나 지원 완료를 뜻하지 않습니다. 따라서 카탈로그의 기본 명칭은 **‘제출용 파일’**로 정합니다.

공통 이력서와 공고별 맞춤 이력서의 역할을 명시합니다. 공통 원본 수정이 이미 생성된 모든 맞춤본을 갱신했다고 암시하지 않습니다. 과거 자료를 보존하고 현재 문서와의 관계를 실제 기록 범위 안에서 설명합니다.

## 5. 화면 밀도는 판단과 읽기에 맞춥니다

기본 화면은 지금 처리할 공고와 다음 행동을 먼저 보여줍니다. 핵심 통계만 앞에 두고, 상세 집계·운영 로그·파일 경로는 보조 정보로 배치합니다. `Publish`, `Drafts` 같은 내부 이름은 필요한 운영 상세에서 확인하게 합니다.

데스크톱 목록은 비교하기 쉬운 정렬된 행을 사용합니다. 모바일에서는 같은 내용을 읽는 순서에 맞춰 세로로 배치하고 긴 상세만 접습니다. 페이지 전체의 가로 넘침이나 잘린 행동 버튼을 허용하지 않습니다. 문서의 넓은 표·코드는 해당 영역 안에서 스크롤합니다.

목록에서는 정보 밀도를 유지하고, 이력서·보고서·초안 본문은 16px 글자와 70~78자 안팎의 읽기 폭을 사용합니다. 핵심 행동과 상태는 화면 크기와 무관하게 접근할 수 있어야 합니다. 필요한 정보가 보이지 않는 문제를 여백이나 접기만으로 해결하지 않습니다.

## 6. 탐색은 다섯 업무 영역으로 고정합니다

| 주 메뉴 | 포함하는 업무 |
| --- | --- |
| 검토함 | 승인 대기, 받은 제안 |
| 후보 | 선택한 공고의 우선순위 검토와 관리 |
| 지원서류 | 공고별 초안, 제출용 파일 |
| 이력서 | 공통 원본, 수정 대화, 이력, 갱신 제안 |
| 자료 | 조사 보고서, 참고 문서, 사실베이스 |

주 메뉴는 업무 영역, 보조 메뉴는 해당 영역의 목록 종류, 문서 탭은 현재 공고의 문서 종류입니다. 기존 URL과 직접 접근을 유지하며, 내부 구현이나 파일 종류가 추가될 때마다 주 메뉴를 늘리지 않습니다.

데스크톱은 **아이콘과 글자 라벨이 함께 있는 176px 사이드바**, 좁은 화면은 다섯 항목의 하단 탐색을 사용합니다. 하단 safe area와 콘텐츠 여백을 확보합니다. 전역 메뉴의 활성 배경, 보조 메뉴·문서 탭의 밑줄, 필터의 선택 표시를 구별합니다. 라우트 이동은 링크, 같은 화면의 문서 전환은 탭, 조건 선택은 필터로 구현합니다.

이후 면접 준비나 지원 결과 기능이 필요해져도 먼저 공고 상세와 기존 업무 영역에 연결합니다. 독립적으로 반복 사용하는 업무라는 근거가 생겼을 때만 주 메뉴를 재검토합니다. 이번 디자인 결정으로 새로운 지원 추적·알림·자동 지원 기능을 추가하지 않습니다.

## 7. 시각 규칙은 차분하고 일관되게 유지합니다

Sharer에서는 내용 우선, 명확한 대상과 행동, 조작 크기, 상태·복구 표시를 가져옵니다. Job Scouter의 긴 근거와 비교 목록에 맞게 적용하며 정적 HTML·JS를 React로 직접 옮겨 붙이지 않습니다.

| 요소 | 확정 기준 |
| --- | --- |
| 기본 면 | 흰색, 보조 면 `#f5f5f6`, 경계 `#ececef` |
| 글자 | 본문 `#18181b`, 보조 `#66666d`; 시스템 글꼴 사용 |
| 크기 | 페이지 제목 24px, 읽기 본문·모바일 입력 16px, 목록 14px, 보조 정보 12~13px |
| 간격 | 4·8·12·16·20·24·32px |
| 형태 | 콘텐츠 면 8px, 버튼·입력 12px radius. 주요 조작 영역 최소 44px |
| 링크·초점 | 기존 파랑 `#1f5fbf`; 링크 의미와 키보드 초점에 사용 |
| 주요 행동 | 짙은 중립색. 대상 영역에서 가장 중요한 행동만 강조 |
| 상태 색 | 초록은 확인된 긍정·성공, 노랑은 주의·확인 필요, 빨강은 명시적 위험·오류·파괴적 행동. 텍스트를 함께 표시 |
| 선택 상태 | 색에 더해 배경·테두리·밑줄과 적절한 접근성 속성 사용 |
| 움직임 | 피드백에 필요한 짧은 전환만 사용하고 동작 감소 설정 존중 |

점수에 따라 전체 카드를 채색하거나, 장식용 큰 통계·그라데이션·유리 효과를 추가하지 않습니다. 읽기와 조작이 안정적인 라이트 화면을 먼저 완성합니다. 키보드 초점, 확대, 충분한 대비, 로딩·빈 상태·오류는 모든 공통 컴포넌트의 기본 책임입니다.

## 변경의 판단 기준

새 화면과 컴포넌트는 다음 질문으로 검토합니다.

1. 어떤 대상에 대한 어떤 결정을 돕는가?
2. 그 결정에 필요한 근거와 불확실성을 행동 전에 볼 수 있는가?
3. 누르면 무엇이 바뀌고, 자동으로 이어지는 작업은 무엇인가?
4. 실패하거나 다른 화면에 다녀와도 맥락과 작업 내용을 유지하는가?
5. 동일한 개념이 다른 탭에서도 같은 이름·상태·조작으로 표현되는가?

완료 판단은 사용자가 **대상·판단 근거·현재 상태·다음 행동**을 설명할 수 있는지로 합니다. 기존 컴포넌트와 데이터 경계를 재사용하고, 반복된 문제를 해결하는 데 필요한 만큼만 공통화합니다. 정확한 표현과 작업 연속성이 확보된 뒤 시각적 세부를 조정합니다.
