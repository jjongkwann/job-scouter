# job-scouter v2 (Phase 6~8) Implementation Plan
> 2026-08-26 사설 디렉터리에서 이전. 개인 인프라 정보(LAN 주소·절대경로·데이터 repo 이름·계정)는 중립 표기로 치환했다. 치환 전 원본은 저장소 밖에 남아 있다.


> **For agentic workers:** task당 서브에이전트 1개, 리뷰 세리머니 생략(프로젝트 규칙). 체크박스로 진행 추적.

**Goal:** 일일 무인 스캔 → 웹 승인 → 등재·지원서류 초안, 주 1회 PKB 기반 이력서 갱신 제안 — 전부 서버 컨테이너에서.

**Architecture:** 워크플로 4개(`DailyScan`·`Publish`·`ResumeSync`·`ApplyResume`)가 기존 `JobScoutCycle`을 대체한다. 상태는 데이터 repo 파일(`jobfeed/proposals.json`, `jobfeed/resume_proposals.json`)이며 모든 자동 변경은 commit+push. `web` 컨테이너(FastAPI :8090)가 파일을 읽어 보여주고, 승인 버튼은 Temporal client로 워크플로를 시작한다. LLM 호출은 전부 `judge.py`의 `_claude()` 경유.

**Tech Stack:** 기존 + fastapi, uvicorn, jinja2, markdown(py). 테스트는 fastapi TestClient.

**Spec:** `docs/specs/2026-08-25-v2-design.md`. (작성 당시엔 저장소 밖 사설 디렉터리에 있었고, 2026-08-26에 스크럽 후 이전했다.)

## Global Constraints
- 공개 저장소: IP·경로·이름·회사명 하드코딩 금지, 전부 env/파일. 데이터 repo 레이아웃(jobfeed/, references/, applications/, drafts/, JK.md)은 `config.py` 상수로.
- `JobScoutCycle`은 제거한다(하위 호환 유지 금지). 관련 테스트는 새 워크플로 테스트로 교체.
- 결정론: 워크플로에서 파일·시계·네트워크 금지. 새 IO는 전부 activity.
- LLM 호출은 `judge._claude()`만. io·workflow·web 모듈은 judge를 import하지 않는다(테스트 유지). web은 Temporal client만 쓴다.
- 토큰 절약: 판정 캐시키 유지, 신규 0건이면 LLM 0, ResumeSync는 해시 게이트, 지원서류는 승인 건만.
- 웹앱은 LAN 전용(:8090), 무인증. 쓰기 액션은 전부 워크플로 시작(파일 직접 수정 금지).
- 테스트: `uv run pytest -q` 전부 통과. 유닛당 러너블 체크 1개(ponytail).
- 커밋은 task마다 1회.

### Task 1: DailyScan / Publish 워크플로 + proposals.json
**Files:** config.py, io_acts.py, workflow.py, worker.py, tests/test_workflow.py, tests/test_io_acts.py

**Interfaces (Produces):**
- `config.ScanParams(budget_tokens=2_000_000, chunk=8, max_usd=0.5)`; `config.PublishParams(ids: list[str], rejects: list[dict] = [])` — rejects 항목 `{"id","why"}`; `config.PROPOSALS = "proposals.json"`(JOBFEED 아래).
- `io_acts.save_proposals(judged: list[dict]) -> int` — 기존 proposals.json 로드 → 비제외 judged 병합(id 키; 필드: id, company, title, url, src, scores, total, reason, quotes, confidence, rubric_version, judged_at?는 workflow.now()가 아니라 activity에서 `date.today().isoformat()`) → candidates rows/skipped에 있는 id 제거 → 저장 → `git add jobfeed/proposals.json && commit "job-scouter: proposals N건" && push`(원격 있을 때). 변화 없으면 커밋 생략. 반환: 현재 proposals 건수.
- `io_acts.load_proposals(ids: list[str]) -> list[dict]` — proposals에서 해당 id 판정 dict(commit_rows 입력 형식) 반환.
- `io_acts.reject_proposals(rejects: list[dict]) -> int` — candidates.json `skipped[id] = [company, title, why]` 추가 + proposals에서 제거 + commit("job-scouter: 제외 N건")+push.
- `io_acts.commit_rows`는 그대로(승인 행 추가 + push). 추가로 등재된 id를 proposals에서 제거하는 것은 `save_proposals([])` 호출로 처리(정리 로직 재사용).
- `workflow.DailyScan.run(p: ScanParams) -> dict`: sync_repo → run_script(fetch_jobs.py) → load_targets → (0건이면 바로 save_proposals([]) 후 반환) → 청크 judge(기존 로직 이식: fetch_requirements → search_context → judge, 예산 강등) → save_proposals(비제외) → 반환 {targets, judged, excluded, demoted, failed, spent_tokens, proposals}. query `status`.
- `workflow.Publish.run(p: PublishParams) -> dict`: sync_repo → load_proposals(ids) → commit_rows(approved) → reject_proposals(rejects) → save_proposals([]) → run_script(refresh_due.py) → run_script(build.py) → [T5 훅: draft_application×approved] → report(stats) → 반환. id는 `publish-{ids hash}` 형태가 아니라 CLI/web에서 `f"publish-{uuid}"`.
- worker CLI: `scan [--budget]`(id `daily-scan-manual`), `publish id1 id2 ...`, `reject <id> "<사유>"`, `status`(실행 중 DailyScan/Publish 아무거나), `schedule` → `daily-scan` 스케줄(cron `7 9 * * *`, Asia/Seoul, overlap SKIP)로 DailyScan 시작 + 기존 `job-scout-weekly` 삭제(`client.get_schedule_handle("job-scout-weekly").delete()`; 없으면 무시). `browser-done`·`approve` 서브커맨드 삭제.

- [ ] 구현 + JobScoutCycle·browser_done·approve 제거
- [ ] tests: test_workflow.py 재작성 — DailyScan(신규 4건 중 2건 비제외 → save_proposals 스텁이 2건 받음, 예산 강등 케이스 유지), Publish(ids 1건 → commit_rows 스텁에 그 1건, rejects 1건 → reject_proposals 스텁). test_io_acts.py — save_proposals 병합·정리(tmp jobfeed: candidates rows에 있는 id는 제거), reject_proposals가 skipped에 [company,title,why]로 기록.
- [ ] `uv run pytest -q` 통과 → 커밋 `feat: DailyScan/Publish 분리 + proposals.json`

### Task 2: 웹앱 (FastAPI :8090) + compose web 서비스
**Files:** jobscouter/web.py, deploy/compose.yaml, pyproject.toml, tests/test_web.py, README.md

**Interfaces:** `web.app` (FastAPI). 환경: config 상수(JOBFEED 등) + TEMPORAL. 의존성 `uv add fastapi "uvicorn[standard]" jinja2 markdown`.
라우트:
- `GET /` 대시보드: proposals.json 표(총점 desc; 회사·포지션(링크)·점수 5축·conf·사유·인용 접기) + 각 행 체크박스 승인/거부(거부 사유 input) → `POST /publish` (form: approve ids, reject id:why) → Temporal `start_workflow(Publish.run, PublishParams(...), id=f"publish-{uuid}", task_queue=Q_WF)` → 302 `/`. 하단: 「평판 미조사 회사」= proposals 회사 중 기업평판.md에 없는 회사(회사명 정규화 `_norm` 재사용은 io_acts import 없이 web에 동일 함수 복사 금지 → `jobscouter/config.py`로 `_norm` 이동 후 양쪽 import). 「최근 실행」= Temporal `list_workflows("WorkflowType='DailyScan' OR WorkflowType='Publish'")` 최근 5건 상태.
- `GET /candidates` → `jobfeed/후보목록.html` 그대로 반환(없으면 안내).
- `GET /reports`, `/reports/{name}` → jobfeed/reports/*.md 목록·렌더(markdown).
- `GET /resume` → JK.md·references/이력서_사실베이스.md·drafts/*.md 탭 렌더. `/resume/proposals`는 T6에서 추가.
- `GET /applications`, `/applications/{slug}` → applications/*/ 5종 md 렌더.
- `GET /docs`, `/docs/{path}` → references/ md 렌더(하위 디렉토리 포함, `..` 차단).
- 스타일: 인라인 CSS 한 블록, 다크 모드 없음. 템플릿은 web.py 안 문자열 + jinja2 `Environment(autoescape=True)`. 마크다운은 `markdown` 패키지(extensions: tables, fenced_code).
- compose: `web` 서비스 — 같은 이미지, `command: ["uv","run","uvicorn","jobscouter.web:app","--host","0.0.0.0","--port","8090"]`, ports `8090:8090`, volumes `${DATA_REPO}:/work/repo`(ro 아님 — 후보목록.html 읽기만이지만 단순화), environment 동일 6개, depends_on temporal.
- [ ] tests/test_web.py: tmp JOBFEED(proposals 1건·후보목록.html·reports 1개·JK.md·사실베이스) 만들고 TestClient로 `/`(회사명 표시), `/candidates`, `/reports/<name>`, `/resume`, `/docs/../etc` 400 확인. `/publish`는 Temporal client를 monkeypatch(`web.start_publish` 함수로 분리)해 PublishParams 인자 검증.
- [ ] 커밋 `feat: 웹앱 — 대시보드·승인·열람`

### Task 4: (Phase 7) 지원서류 5종 초안
**Files:** io_acts.py(fetch_posting_full, write_application), judge.py(draft_application), workflow.py(Publish 훅), config.py(APPLICATIONS="applications"), tests

**Interfaces:**
- `io_acts.fetch_posting_full(t: Target) -> str` — 원티드 `/api/v4/jobs/{id}`: position·company.name·detail.{intro,main_tasks,requirements,preferred_points,benefits} 전문 / 점핏 `position/{id}`: title·companyName·responsibility·qualifications·preferredRequirements. 캡 6000자.
- `io_acts.write_application(company: str, files: dict[str,str]) -> str` — slug = 회사명 정규화(영문 소문자·숫자·`_`, 한글은 그대로) → `applications/{slug}/` 생성, 5개 md(0_JD.md, 1_맞춤_이력서.md, 2_자기소개서.md, 3_면접지식맵.md, 4_포트폴리오_구성.md) + README.md(파일 목록·지원 전 체크리스트 스텁) 쓰기, commit("job-scouter: {회사} 지원서류 초안")+push. 이미 폴더 있으면 `_draft` 접미(사람 작업 덮어쓰기 금지).
- `judge.draft_application(company, title, posting: str) -> dict[str,str]` — `_claude(prompt, system, max_usd=1.0)`; system = 사실베이스 + JK.md + `applications/README.md`(규칙) + 예시 1개사 5종(형식 앵커, `config.APP_EXAMPLE` env 기본 "example"); prompt = 공고 전문 + "5개 문서를 `=== FILE: 이름 ===` 구분자로 출력. 사실베이스에 없는 주장 금지". 구분자로 split → dict. 5개 미만이면 RuntimeError(재시도).
- Publish: build 뒤 approved 각각 `fetch_posting_full → draft_application → write_application`(llm·io 큐). 실패는 개별 기록(전체 실패 아님).
- [ ] tests: `_claude` 모킹으로 split 검증, write_application tmp 디렉토리·중복 폴더 `_draft`.
- [ ] 라이브: 승인 1건에 대해 실행 → applications/{회사}/ 5종 확인(메인 세션)
- [ ] 커밋 `feat: 승인 공고 지원서류 5종 초안`

### Task 5: (Phase 8) ResumeSync / ApplyResume
**Files:** io_acts.py(pkb_snapshot, save_resume_proposals, apply_resume, reindex_facts), judge.py(propose_resume_update), workflow.py, worker.py, web.py(/resume/proposals), tests

**Interfaces:**
- `io_acts.pkb_snapshot() -> dict{"hash": str, "text": str, "docs": int}` — ES `pkb_documents`에서 PKB의 curated 프로필 필터를 그대로 재현: 실행 전에 서버 `personal-docs/src/pkb/retrieve.py`의 `profile_filter("curated")`·`_lifecycle_filter`가 만드는 ES 필터(status/doc_type/archived)를 읽어 동일 쿼리를 쓴다(값을 추측하지 말 것). 카테고리는 경력·프로젝트·이력 관련만: `category` terms 집계를 먼저 찍어 보고 선택(계획서 밖 값이므로 선택 근거를 커밋 메시지에). `content`를 doc_id 순으로 이어 붙여 sha256 → hash; text는 40k자 캡(초과 시 doc 단위로 자르고 잘렸음을 표기).
- `judge.propose_resume_update(snapshot_text, factbase, jk) -> list[dict]` — `_claude` + json-schema `{proposals:[{target: "factbase"|"JK.md", section, current(원문 인용 또는 ""), proposed, evidence(PKB 문서 제목·발췌), kind: add|change|remove}]}` (reason 류 긴 필드는 마지막). 규칙: 사실베이스·JK.md에 이미 있는 내용은 제외, 날짜·숫자는 PKB 원문 그대로, 추정 금지.
- `io_acts.save_resume_proposals(items, hash) -> int` — `jobfeed/resume_proposals.json`{hash, items[{id: sha1(target+section+proposed)[:8], ...}]} 저장 + `data/resume_state.json`에 hash 저장 + commit/push.
- `workflow.ResumeSync.run()`: sync → pkb_snapshot → activity `resume_state_hash()`(data/resume_state.json 읽기) → 같으면 {"changed": False} 반환(LLM 0) → 다르면 propose → save.
- `io_acts.apply_resume(ids) -> str` — 승인 항목: kind=change면 `current` 문자열을 `proposed`로 치환(정확 매칭 실패 시 해당 항목 건너뛰고 보고), add면 target 파일 끝 `## 미분류 추가(자동 제안 승인)` 절에 append, remove면 current 삭제. 반영된 항목은 proposals에서 제거. commit("resume: 자동 제안 반영 N건")+push.
- `io_acts.reindex_facts()` — `scripts/index_es.py`의 facts 부분만 재실행(함수로 분리해 import).
- `workflow.ApplyResume.run(ids)`: sync → apply_resume → reindex_facts.
- worker: `resume-sync`(수동 시작), `apply-resume id...`, `schedule`에 `resume-sync` 주간(월 08:00 KST) 추가.
- web: `/resume/proposals` — 항목 표(대상·섹션·현재→제안·근거) 체크 → `POST /resume/apply` → ApplyResume 시작.
- [ ] tests: pkb_snapshot은 ES 클라이언트 monkeypatch(hits 2건 → hash 결정적), apply_resume tmp 파일 치환/append, 워크플로 hash 동일 시 propose 스텁 미호출.
- [ ] 라이브: 서버에서 `resume-sync` 1회 → 변화 없음 경로(LLM 0) 확인 → 사실베이스 임시 수정 없이 PKB 문서 하나 갱신 후 재실행 → 제안 생성 → 웹 승인 → 반영·재색인(메인 세션)
- [ ] 커밋 `feat: ResumeSync/ApplyResume — PKB 기반 이력서 갱신 제안`
