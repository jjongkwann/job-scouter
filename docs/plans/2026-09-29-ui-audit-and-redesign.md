# Job Scouter 화면 점검과 수정 계획

점검·구현일: 2026-09-29. 범위: 현재 배포 화면, 로컬 `web/`의 전체 페이지 구조와 공통 컴포넌트, `../sharer`의 디자인 규칙과 구현. 최초 점검 이후 사용자의 구현·테스트·배포 요청에 따라 아래 계획을 제품 코드에 적용했습니다. 2절과 3절의 수치·문제는 개편 전 점검 기록입니다.

후속 결정: [디자인 원칙](../design.md)을 이번 개편과 이후 UX의 기준으로 확정했습니다. 아래 수정 계획도 필수 판단 근거의 상시 표시, 업무 연속성, 실제 기록에 따른 상태 표현을 따릅니다.

## 1. 결론

공통 `Page`, `Nav`, `Fit`, `Due`, `ScoreCells`, `Markdown`이 있어 통일할 기반은 있습니다. 다만 기존 화면을 옮긴 도메인 CSS와 shadcn 스타일, 새로 추가된 파일 카드가 서로 다른 규칙을 사용합니다. 페이지마다 CSS를 덧붙이면 선택 상태와 반응형 충돌이 계속 생깁니다.

먼저 실제로 깨지는 표·탭·모바일 필터를 고치고, 공통 토큰과 메뉴 구조를 정리한 다음 목록·상세 화면을 같은 규칙으로 바꾸는 순서가 적절합니다. Sharer의 색·간격·조작 크기·탐색 원칙을 기존 React/Base UI 컴포넌트에 적용합니다. 별도 UI 라이브러리나 공용 패키지는 필요하지 않습니다.

## 2. 확인한 범위와 배포 차이

| 구분 | 이번에 확인한 내용 |

## 4. 확정한 메뉴 구조와 화면 간 관계

주 메뉴는 다섯 개로 묶고 기존 URL은 유지합니다. 주 메뉴는 업무 영역, 영역 안의 보조 메뉴는 목록 종류, 상세의 문서 탭은 열린 문서 종류를 나타냅니다. 세 단계를 같은 검은 알약 모양으로 표시하지 않습니다.

| 주 메뉴 | 보조 화면과 기존 경로 | 역할과 다음 행동 |
| --- | --- | --- |
| 검토함 | 승인 대기 `/`, 받은 제안 `/offers` | 수집 공고를 후보로 승인하거나, 받은 제안의 근거를 확인. 원티드 답변은 원티드에서 수행 |
| 후보 | `/candidates` | 추천도·적합도·마감·평판으로 검토하고 해당 공고의 지원서류 상세로 이동 |
| 지원서류 | 공고별 초안 `/applications`, 제출용 파일 `/applications/files` | 공고 맥락을 유지하며 초안 검토, 파일 열람·다운로드. 파일 생성과 사용자 검토 완료를 구별 |
| 이력서 | `/resume`, 이력·대화·갱신 제안 | 공통 이력서 원본을 관리. 공고별 맞춤본과 역할 구별 |
| 자료 | 조사 보고서 `/reports`, 참고 문서 `/docs` | 판단 근거와 사실베이스 확인. 연결이 확인된 경우 관련 공고·제안으로 이동 |

사용 흐름은 다음과 같습니다.

1. 승인 대기 → 후보 승인 → 후보목록 → 공고별 지원서류 → 초안 검토 / 완성본 확인.
2. 받은 제안 → 원문·조사 보고서·평가 확인 → 연결된 후보 또는 지원서류. 외부 답변과 내부 후보 승인은 별개입니다.
3. 공통 이력서·사실베이스 → 판정 및 맞춤 초안의 근거. 화면 이동만으로 문서 동기화나 재생성을 실행하지 않습니다.
4. 보고서·참고 문서 → 관련 업무를 설명하는 자료. 모든 보고서를 특정 공고에 억지로 연결하지 않습니다.

탐색 표현:

- 데스크톱: 176px 왼쪽 탐색 영역에 아이콘과 이름을 함께 고정합니다. 콘텐츠 너비를 기준으로 목록 배치를 결정합니다.
- 모바일: 다섯 메뉴를 하단에 배치하고 safe area·본문 하단 여백을 확보합니다. 보조 메뉴는 페이지 제목 아래에 둡니다.
- 목록 상세: `지원서류 / 공고별 초안 / 회사·포지션`처럼 현재 위치와 상위 링크를 표시합니다.
- 동일 회사에 여러 공고·폴더가 있는 경우 공고 ID와 폴더 선택을 보존합니다. 목록 합치기를 이유로 데이터나 파일을 삭제하지 않습니다.

## 5. Sharer에서 적용할 규칙

기준: `../sharer/docs/design.md:13-21,61-71`, `../sharer/web/styles.css:1-16,66-200,790-831`.

| 항목 | 적용안 | Job Scouter에서의 조정 |
| --- | --- | --- |
| 색 | 흰 면, 본문 `#18181b`, 보조 글자 `#66666d`, 보조 면 `#f5f5f6`, 경계 `#ececef` | 평판·마감·오류의 의미 색 유지. 분홍 accent를 모든 카드와 링크에 복사하지 않음 |
| 간격 | 4·8·12·16·20·24·32px | 페이지별 9·11·14·18px 임의값을 공통 규칙으로 정리 |
| 글자 | 제목 24px, 읽기 본문 16px, 목록 14px, 메타데이터 12~13px | 점수·숫자는 tabular 유지. 10px 전후 텍스트에 중요한 정보를 맡기지 않음 |
| 조작 | 주요 버튼·입력 최소 44px, 모바일 입력 16px | 데스크톱 정보 밀도와 터치 조작을 구분. 버튼·링크·선택 상태를 일관되게 표시 |
| 형태 | 버튼·입력 12px, 콘텐츠 면 8px radius | 기존 Card를 먼저 통일. 미디어 타일의 3:4 비율은 가져오지 않음 |
| 탐색 | 데스크톱 rail, 모바일 라벨 포함 하단 메뉴 | Sharer의 보관함·업로드 대신 위의 다섯 업무 영역 적용 |
| 상태 | 로딩·빈 목록·검색 결과 없음·실패 구별 | 처리 실패와 복구 행동을 화면에 남김. 토스트만으로 설명하지 않음 |
| 접근성 | 명확한 초점, 건너뛰기, 선택 의미, 동작 감소 | 확대 제한은 복사하지 않음. 기존 Base UI 키보드 동작 유지 |

Sharer는 정적 HTML/CSS와 직접 DOM을 다루는 JS 구현입니다. 파일을 import해 React 컴포넌트로 쓸 수는 없습니다. 디자인 규칙과 필요한 마크업 구조를 옮기고, 이미 설치된 Base UI·Tailwind·Lucide를 사용합니다.

| `app/page.tsx`, `app/candidates/page.tsx` | 큰 표를 요약 행+상세로 재배치, 필터·선택 작업 정리 | 승인·후보 |
| `app/offers/page.tsx` | 원티드 응답 상태·내부 평가 상태·평판을 구별, 보고서 연결 유지 | 받은 제안 |
| `app/applications/`, `components/application-files.tsx` | 초안/완성본 보조 탐색, 문서명·파일 행동·공고 맥락 통일 | 지원서류 전체 |
| `components/markdown.tsx`, 문서 CSS | 보고서·이력서·초안의 본문 폭·제목 계층·표·링크 표시 통일 | 문서 열람 전체 |
| `app/reports/`, `app/docs/`, `app/resume/` | 목록 표기·상위 이동·보조 행동·오류와 빈 상태 통일 | 자료·이력서 |
| `jobscouter/api.py`, `web/lib/api.ts` | 보고서 목록의 표시 메타데이터만 보완 | 보고서 |

중복이 실제로 있는 상태 안내와 공고 제목 영역만 작은 컴포넌트로 추출합니다. 모든 목록을 처리하는 범용 테이블, 별도 디자인 시스템 패키지, 테마 설정 프레임워크는 만들지 않습니다. 추천도·평판·마감 계산은 기존 서버를 계속 사용합니다.

## 7. 구현 순서와 단계별 완료 기준

### 0단계 — 작업 기준 확정

- 기존 tracked/untracked 변경 목록과 배포 자산 차이를 기록합니다. 다른 작업의 변경을 일괄 커밋하거나 덮어쓰지 않습니다.
- 받은 제안·완성본·슬라이드의 로컬 구현 중 이번 UI에 포함될 기준을 분리합니다. 설치·서버 변경 없이 로컬 실행에 필요한 API 경로를 확인합니다.
- 기존 경로·공고 ID·초안 폴더·완성본 파일을 유지합니다. 저장 형식 변경은 이 계획에 필요하지 않습니다.
- 완료 기준: 기준 소스로 앱이 실행되고 메뉴/API 대응 목록이 확인됩니다.

### 1단계 — 공통 스타일 충돌과 조작 문제 해결

- `--accent`/링크 토큰 충돌을 제거하고 Card/Button/Input/Badge의 크기·경계·색을 정합니다. 기존 토큰 사용처는 함께 교체해 중복 체계를 남기지 않습니다.
- `DocTabs`는 밑줄 스타일로 통일하고 파일명 대신 `공고`, `맞춤 이력서`, `자기소개서`, `면접 준비`, `포트폴리오 구성`을 표시합니다. 파일 키는 그대로 유지합니다.
- 모바일 필터의 가로 넘침과 내비게이션 줄바꿈을 해결합니다. 표는 아래 3단계의 최종 목록 구조로 이어질 수 있게 상시 표시 정보부터 줄입니다.
- 완료 기준: 선택된 탭 이름이 보이고, 390·1093·1280px에서 주요 버튼·열이 가려지지 않습니다. 다음 단계 전 현재 메뉴로도 전체 기능을 사용할 수 있어야 합니다.

### 2단계 — 탐색·페이지 구조 통일

- 다섯 주 메뉴와 영역별 보조 탐색을 적용합니다. 기존 URL을 유지하므로 새 라우트·리디렉션 계층은 만들지 않습니다.
- Page에 필요한 상위 링크와 행동 영역을 추가하고 실제 상세 페이지에 적용합니다.
- 승인/거부, 페이지 이동, 문서 탭, 필터를 서로 다른 역할에 맞게 표시합니다. `aria-current`와 `aria-selected`를 해당 역할에 사용합니다.
- 완료 기준: 모든 기존 화면에 도달하고, 상세에서 상위 영역으로 돌아갈 수 있으며, 모바일 하단 메뉴가 내용·작업 버튼을 가리지 않습니다.

### 3단계 — 업무별 목록·상세 정리

- 공고 행 기본 정보: 회사·포지션, 확인된 필수 자격의 미충족·미확인 항목, 마감·근무지, 짧은 판정 사유, 적합도와 추천도, 평판·문서 상태, 행동. 자격 미충족·중요한 감점 이유·응답 기한은 항상 보입니다.
- 세부 점수, 긴 판정 설명과 전체 인용은 같은 행의 상세에 배치합니다. 출처·확인 시점은 판단 내용 가까이에 표시합니다. 모바일에서는 점수를 한 항목씩 길게 세우지 않고 묶어서 표시합니다.
- 정렬은 native select, 자주 쓰는 필터는 즉시 표시, 나머지는 명시적인 ‘추가 필터’ 아래에 둡니다. 기존 필터 조합과 저장 상태를 보존합니다.
- 후보 선택·삭제·승인 처리 중 잠금, 오류, 선택 건수, 초안 실행 상태를 유지합니다. 후보 승인은 기존 후속 초안 생성을 시작한다는 점을 안내합니다. 화면 이동·열람만으로 새 작업을 실행하지 않습니다.
- 지원서류에 `초안 5종`과 `제출용 파일`을 명시하고 `미지원` 추정을 제거합니다. 파일 생성·사용자 검토·실제 지원을 구별하고 다운로드 행동은 보기/받기로 구분합니다.
- 완료 기준: 후보→공고 상세→초안/완성본, 받은 제안→근거 보고서/연결 공고의 경로가 일관되고 같은 상태가 같은 용어로 보입니다.

### 4단계 — 보고서·문서와 전체 회귀 확인

- 보고서 날짜는 확인된 날짜만 사용합니다. 종류는 일일 요약·공고 조사·받은 제안 조사·면접 준비 등 실제 자료와 맞게 분류합니다. 제목은 문서 제목을 우선 사용하고, 제목 없는 문서는 원래 이름을 표시합니다.
- 파일명·URL·원문은 보존하고 화면에 필요한 읽기 메타데이터만 보완합니다. 원본 수정일을 조사일인 것처럼 표시하지 않습니다.
- 문서/이력서/초안의 본문 링크, 긴 제목, 표 스크롤, 코드 블록, 화면 제목과 문서 제목 계층을 점검합니다.
- 완료 기준: 모든 주요 메뉴·상세 경로의 정상/로딩/빈 상태/오류 표시가 일관되고 아래 검증 항목을 통과합니다.

## 8. 구현 시 실행할 검증

아래 항목을 구현 검증 기준으로 사용했습니다. 실제 실행 결과와 한계는 9절에 기록합니다.

- 기존 웹 검사: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` (`web/`에서 실행).
- 보고서 API 변경 시 기존 `tests/test_api.py`에 날짜 기반·공고 기반·제안 기반 파일명의 소규모 회귀 사례를 추가하고 해당 테스트를 실행합니다. 기존 Markdown과 ID가 보존되는지도 확인합니다.
- 기존 Vitest 패턴으로 메뉴 활성화, 탭 선택, 후보 필터·선택 상태 등 변경되는 동작을 검증합니다. 단순 CSS 문자열과 픽셀값만 단언하는 테스트는 만들지 않습니다.
- 실제 브라우저에서 360·390·768·1060·1093·1280·1440px을 확인합니다. 페이지 자체의 가로 넘침이 없어야 하며, 긴 문서 표는 표시된 영역 안에서 스크롤 가능해야 합니다. `scrollWidth`뿐 아니라 숨겨진 자식의 경계도 확인합니다.
- 키보드로 주 메뉴·보조 메뉴·문서 탭·필터·선택·상위 이동을 확인합니다. 선택한 탭은 hover 여부와 무관하게 읽혀야 합니다.
- 긴 회사/포지션/파일명, 동일 회사의 여러 공고, 초안 없음·생성 중·생성 실패·완료, 완성본 없음, 검색 결과 없음, 요청 오류를 로컬 테스트 데이터로 검사합니다.
- 운영 데이터로 승인·삭제·재생성 회귀를 실행하지 않습니다. 해당 쓰기 동작은 로컬의 격리된 검증 데이터/API에서 확인합니다.
- 실물 iPhone/Safari와 보조기기 확인은 뷰포트 모의 검사와 별도로 기록합니다.

## 9. 구현 결과와 검증 기록

- 디자인 원칙을 `docs/design.md`에 확정하고 다섯 업무 영역, 공통 색·글자·조작 크기, 데스크톱 사이드바와 모바일 하단 탐색을 적용했습니다.
- 승인·후보 목록을 판단 근거가 보이는 요약 행과 펼칠 수 있는 상세로 정리했습니다. 보조 통계·추가 필터는 접을 수 있고 선택 작업 막대는 선택/처리 중에만 표시됩니다.
- 기존 공고 ID·URL·폴더를 보존하고, 후보로 돌아올 때 필터·정렬·해당 공고 위치를 복원합니다. 문서 탭은 읽기 쉬운 이름과 밑줄 선택 표시를 사용합니다.
- 초안·제출용 파일·원티드 응답 상태를 분리했습니다. 등록 메모를 평판으로 표시하지 않으며 보고서 날짜는 실제 날짜 접두만 인정합니다.
- 이미 로컬에 있던 받은 제안·파일·슬라이드 읽기 API와 화면을 배포에 포함합니다. 생성된 개인정보 문서·이미지·슬라이드 원본은 코드 커밋과 Docker 빌드 문맥에서 제외합니다.
- 웹 lint·typecheck·25개 테스트·프로덕션 빌드, Python `pytest tests -q` 190개 테스트가 통과했습니다. 루트 전체를 대상으로 한 최초 pytest 호출은 무시된 과거 릴리스의 테스트까지 수집해 충돌했으며, 실제 테스트 폴더를 지정해 전체 검사를 완료했습니다.
- Chrome 프로덕션 화면에서 후보·보고서 목록을 360·390·768·1060·1093·1280·1440px로 확인했습니다. 후보 선택 막대와 하단 메뉴가 겹치지 않고, 문서 표는 본문 영역 안에서 가로 스크롤됩니다. 문서 탭의 방향키·Enter 전환, 해당 후보 복귀, 파일 검색 결과/빈 결과를 확인했습니다.
- 승인·후보 제외 요청은 가짜 API로 요청 대상과 처리 상태를 검증했습니다. 운영 데이터로 승인·삭제·초안 생성·이력서 저장은 실행하지 않았습니다. 실물 iPhone·Safari·VoiceOver 검증은 수행하지 않았습니다.
- 배포 대상은 기존 mini의 api·web·io·llm입니다. 기존 실행 이미지를 복구용 태그로 남기고, 배포 후 HTTP·실행 코드·브라우저를 확인합니다. Temporal 저장소와 기존 문서는 보존합니다.
